## 🧬 System Architecture

Aluer ServerGuard deploys on the same host as your Minecraft server, communicating with PaperMC via the **RCON protocol** while managing OS-level firewalls (iptables/ufw) and Cloudflare edge protection.

### 1. Three-Layer Decision Engine

This is the core design — L1 handles strategic decisions, L2 handles signal-level tactical judgment, and L3 handles execution.

```
┌──────────────────────────────────────────────────────────────┐
│                    L1: AluerSovereignEngine                  │
│  Input:  Full-network posture JSON (compressed context)     │
│  Process: Send to DeepSeek LLM for structured directives    │
│  Output: workflow (1 of 8) + defenseLevel + reason          │
│  Cycle:  Every 45 seconds                                   │
│  Trait:  LLM-driven, natural language reasoning, handles    │
│          novel/ambiguous threat patterns                    │
├──────────────────────────────────────────────────────────────┤
│                    L2: AluerKernelEngine                      │
│  Input:  Real-time signals from 5 virtual modules           │
│  Process: Weighted aggregation → 3D pressure → directives   │
│  Output: heat / resonance / control + KernelDirective       │
│  Cycle:  Every 30 seconds (Pulse)                            │
│  Trait:  Deterministic rules, explainable, immune to        │
│          LLM latency/hallucination                          │
├──────────────────────────────────────────────────────────────┤
│                    L3: AIAutonomousService                    │
│  Input:  L1 macro directive + L2 Kernel directive           │
│  Process: Conflict arbitration → cooldown → rate-limit      │
│  Output: ban-ip / kick / whitelist / clear-lag              │
│  Guard:  Max 12 actions/hour, dual-signal for high-risk ops │
└──────────────────────────────────────────────────────────────┘
```

**Why two decision layers?** Sovereign (DeepSeek) excels at understanding novel threats but has API latency (~2-5s) and occasional unstructured output. Kernel is a pure rule engine with <1ms latency, capable of instant reaction to known threat patterns. The two layers intersect and back each other up.

### 2. Kernel Signal Fusion Model

The Kernel runs 5 virtual modules (`KernelModule` interface), each collecting pressure signals from specific security subsystems:

| Module | Name | Data Source | Vector | Baseline Weight |
|--------|------|-------------|--------|-----------------|
| `ThreatMeshModule` | Threat Mesh | DDoS / Firewall / IDS / Port Scan / DPI | `network` | 1.12 |
| `CommandLatticeModule` | Command Lattice | Command Guard (dangerous cmd + RCON brute force) | `command` | 1.18 |
| `HardeningMatrixModule` | Hardening Matrix | Security baseline audit (vuln × severity) | `integrity` | 1.05 |
| `PerimeterWardModule` | Perimeter Ward | WAF (blocked/suspicious + active clients) | `perimeter` | 0.92 |
| `EchoGridModule` | Echo Grid | Historical IP pressure memory decay | `memory` | 0.84 |

Each Pulse cycle (default 30s), 5 modules produce 0~N `KernelSignal` objects. Aggregation algorithm:

```
For each signal:
  weighted = clamp(pressure × adaptiveWeight[module], 0, 100)
  vectorScores[vector] += weighted
  moduleScores[module] += weighted

heat     = clamp(peak_vector × 0.68 + avg_vector × 0.32, 0, 100)
resonance = clamp(heat × 0.45 + second_vector × 0.18 + energized × 14 + count × 2.2, 0, 100)
control  = clamp(100 - heat × 0.62 - resonance × 0.28, 0, 100)
```

Adaptive weights via exponential moving average:

```
target = baseline + (pressure ≥ 80 ? 0.18 : pressure ≥ 55 ? 0.08 : 0)
active = current × 0.82 + target × 0.18
active = clamp(active, 0.72, 1.45)
```

EchoGrid (attacker memory) decay:

```
cell.pressure = cell.pressure × 0.55 + pulse.heat × 0.75
// Cells exceeding retention time are auto-purged
```

## 🚀 Quick Start

### Requirements

| Dependency | Version | Notes |
|------------|---------|-------|
| JDK | 17+ | Compile and runtime |
| Maven | 3.9+ (bundled) | `apache-maven-3.9.6/` included in repo |
| OS | Ubuntu / Debian | Recommended for production; other Linux works but some security modules need iptables/ufw |
| Memory | 2 GB+ free | On top of Minecraft server's own memory |
| Disk | 10 GB+ | Logs + backups + jar |
| Minecraft | PaperMC 1.21+ | RCON must be enabled (`enable-rcon=true` in `server.properties`) |
| DeepSeek | API Key | Required for AI decision and natural language Q&A |
| Node.js | 18+ (dev only) | Production uses pre-built static assets |

### Build

```bash
# 1. Clone the repository
git clone https://github.com/ZpjDev/Aluer.git
cd Aluer

# 2. Build with bundled Maven
./apache-maven-3.9.6/bin/mvn clean package -DskipTests

# 3. Output location
ls -lh target/serverguard.jar
```

The build process also compiles the React frontend via Vite, outputting to `src/main/resources/static/` and embedding into the jar.

### Environment Variables

**Minimum viable config** (only 2 env vars required):

```bash
# Required: DeepSeek API Key (get from https://platform.deepseek.com)
export DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# Required: RCON password (must match rcon.password in server.properties)
export RCON_PASSWORD=your-strong-rcon-password
```

**Full production config**:

```bash
# ──── Core Credentials ────
export DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
export DEEPSEEK_BASE_URL=https://api.deepseek.com
export DEEPSEEK_MODEL=deepseek-chat
export RCON_PASSWORD=your-strong-rcon-password

# ──── Email Alerts (QQ email example) ────
export ALUER_ALERT_SMTP_USERNAME=your-email@qq.com
export ALUER_ALERT_SMTP_PASSWORD=your-smtp-auth-code
export ALUER_ALERT_EMAIL_PRIMARY=admin@example.com
export ALUER_ALERT_EMAIL_SECONDARY=backup@example.com

# ──── Cloudflare Edge Protection (optional) ────
export ALUER_CLOUDFLARE_ZONE_ID=your-zone-id
export ALUER_CLOUDFLARE_API_KEY=your-api-key
export ALUER_CLOUDFLARE_EMAIL=your-cloudflare-email

# ──── Discord/Slack Webhooks (optional) ────
export ALUER_WEBHOOK_DISCORD=https://discord.com/api/webhooks/xxx/yyy
export ALUER_WEBHOOK_SLACK=https://hooks.slack.com/services/xxx/yyy/zzz
```

> **Security note**: Never hardcode API keys or passwords in `application.yml`. All sensitive values use `${VAR_NAME:}` placeholder syntax, defaulting to empty string when not set.

## 📦 Deployment Guide

### Systemd Services

The repo provides two systemd unit files:

**`systemd/minecraft.service`** — Minecraft server (Aluer's prerequisite):

```ini
[Unit]
Description=Minecraft PaperMC Server
After=network.target

[Service]
Type=simple
User=minecraft
WorkingDirectory=/opt/minecraft
ExecStart=/usr/bin/java -Xms4G -Xmx4G -jar paper-1.21.11.jar nogui
Restart=on-failure
RestartSec=10
StartLimitBurst=3

[Install]
WantedBy=multi-user.target
```

**`systemd/serverguard.service`** — Aluer protection system:

```ini
[Unit]
Description=Aluer ServerGuard Protection System
After=network.target minecraft.service
Requires=minecraft.service

[Service]
Type=simple
User=root
WorkingDirectory=/opt/serverguard
ExecStart=/usr/bin/java -jar serverguard.jar
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Deployment steps:

```bash
# 1. Copy service files
sudo cp systemd/minecraft.service /etc/systemd/system/
sudo cp systemd/serverguard.service /etc/systemd/system/

# 2. Create minecraft user
sudo useradd -r -m -d /opt/minecraft minecraft

# 3. Reload systemd
sudo systemctl daemon-reload

# 4. Start Minecraft first, then Aluer
sudo systemctl enable --now minecraft
sudo systemctl enable --now serverguard

# 5. Check status
sudo systemctl status minecraft serverguard

# 6. Watch Aluer logs
sudo journalctl -u serverguard -f
```

### sudo Configuration

Aluer needs permission to run `systemctl restart minecraft`. Copy the sudoers file:

```bash
sudo cp systemd/sudoers.serverguard /etc/sudoers.d/serverguard
sudo chmod 440 /etc/sudoers.d/serverguard
```

### Reverse Proxy (Optional)

When exposing the web console publicly, place Nginx in front:

```nginx
server {
    listen 443 ssl;
    server_name console.your-server.com;

    auth_basic "Aluer Console";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

> **Warning**: Never expose Aluer's port 8080 directly to the internet. The WAF module provides basic protection only and is not a substitute for a proper reverse proxy.

## 🛡️ Defense Levels & Auto Response

### Four-Tier Defense System

The system auto-switches defense levels based on Kernel heat and Sovereign assessment:

| Level | Heat Range | Trigger | Auto Actions |
|-------|-----------|---------|--------------|
| `NORMAL` | < 45 | Normal operation | Routine monitoring, anomalies logged only |
| `ELEVATED` | 45–69 | Single module pressure rise | Increased detection frequency, IP reputation queries enabled |
| `HIGH` | 70–81 | Multiple modules alerting | Auto-block high-risk IPs, rate limiting, edge challenges |
| `LOCKDOWN` | ≥ 82 | Severe compound attack | Whitelist mode, Cloudflare Under Attack, reject new connections, emergency email |

### Mirage Shield Modes

Mirage Shield is the attacker deflection shield with 4 operating modes:

| Mode | Meaning | Auto Trigger |
|------|---------|-------------|
| `OBSERVE` | Observe only, no intervention | Default mode |
| `FORTIFY` | Harden defenses | heat ≥ 78 or threat_score ≥ 85 |
| `MIRAGE` | Mirror deflection | resonance ≥ 72 with high-confidence attacker |
| `SHELTER` | Shelter mode | heat ≥ 82 and resonance ≥ 80, strict rate limiting |

In `MIRAGE` and `SHELTER` modes, deterrence messages are sent to detected attacker IPs.

### Self-Healing Triggers

`AluerSelfHealingOrchestrator` triggers recovery when:

| Condition | Threshold | Recovery Actions |
|-----------|-----------|-----------------|
| TPS emergency | < 12 TPS | `clear-lag` + `kill-entity` + low spawn rate |
| CPU emergency | > 92% | `clear-lag` first, soft restart if ineffective |
| Memory emergency | > 95% | `save-all` → notify players → soft restart |
| Bot Swarm | ≥ 15 concurrent fake players | `whitelist on` + block source IPs |

All recovery actions are log-only when `dry-run=true`.

## ❓ FAQ

<details>
<summary><strong>How do I verify AI is working?</strong></summary>

```bash
aluer> ask Hello
```

If you get an AI response, DeepSeek is configured correctly. Or check logs:

```bash
tail -f /var/log/serverguard.log | grep DeepSeek
```
</details>

<details>
<summary><strong>Not receiving email alerts?</strong></summary>

1. Verify `username`/`password` in email config
2. QQ email requires **authorization code** not login password
3. Check spam folder
4. Run `alert test` to send a test email
</details>

<details>
<summary><strong>Tips for first deployment?</strong></summary>

Enable **dry-run mode** first:

```yaml
serverguard:
  security:
    host-enforcement:
      dry-run: true
    cloud-edge:
      dry-run: true
    self-healing:
      dry-run: true
```

Observe for 1-2 days before disabling dry-run.
</details>

<details>
<summary><strong>Why two decision engines? Won't they conflict?</strong></summary>

No, they're complementary:
- **Sovereign (DeepSeek)**: excels at complex, never-seen attack patterns; 2-5s latency
- **Kernel (rule engine)**: <1ms response, 100% predictable, but can't handle unknown patterns

When outputs disagree, `AIAutonomousService` (L3) resolves based on `autonomy.deepseek-dominant` config. `SecurityOrchestrationService` provides final safety net — no operation exceeds `max-actions-per-hour`.
</details>

<details>
<summary><strong>Performance overhead?</strong></summary>

Tested on 2-core 4GB VPS:
- JVM resident memory: ~180-250 MB (Spring Boot + all services)
- CPU idle: <2% (monitoring and Pulse loops)
- DeepSeek API call CPU: ~5% (mainly network I/O wait)
- No impact on Minecraft server performance (async RCON communication)
</details>
